# 🐻 GRIZZLY — Family Control (GTA 5 RP)

Повноцінний незалежний сайт сім’ї **Grizzly**: публічна сторінка та закрита панель управління українською мовою.

**Технології:** Cloudflare Workers (нативний JavaScript Worker), Cloudflare D1 (SQLite), адаптивний HTML/CSS/JavaScript без зайвих фронтенд-залежностей. Не використовує Google OAuth, Firebase, R2, Discord OAuth або дані інших проєктів.

> Проєкт Grizzly повністю відокремлений від УДО. Жоден файл чи база УДО не використовуються.

**Порожня база:** жодних вигаданих учасників, фінансових операцій або CAPT-результатів. Є лише 15 демонстраційних назв рангів, 6 напрямків та редаговані стартові тексти правил/історії.

## Публічна головна сторінка

Сайт: **https://grizzly-family.online/**. Для гостей він відкриває публічну сторінку. Якщо ви вже авторизовані й автоматично потрапляєте у внутрішню панель, натисніть **«Публічний сайт»** у лівому меню або відкрийте **https://grizzly-family.online/?view=public#home**. Кнопка **«Відкрити панель»** на публічній сторінці повертає до особистого кабінету без виходу.

Всі редаговані тексти (гасло, історія, правила, вимоги та Discord) завантажуються з D1 через `/api/public` і змінюються у внутрішньому розділі **«Налаштування»**. У публічну галерею потрапляють **лише погоджені фото** з розділу «Галерея» (прямі HTTPS-посилання ImgBB). Заявки подаються через незмінний `POST /api/apply`; створення акаунта з заявки не автоматизоване.

## Фотогалерея GRIZZLY

Галерея використовує вже наявні записи `records` у D1. **Нова міграція та R2 не потрібні**.

1. Завантажте власний GTA 5 скриншот на **https://imgbb.com/**.
2. Скопіюйте **прямий HTTPS-URL картинки** (`https://i.ibb.co/.../file.jpg`, `.png`, `.webp` або `.gif`), а не звичайне посилання на сторінку ImgBB.
3. У панелі Grizzly відкрийте **«Галерея» → «Додати фото»**. Вкажіть назву, підпис, категорію (**CAPT / Автомобілі / Збори / Івенти / Інше**) і посилання. Попередній перегляд з’явиться автоматично.
4. Виберіть **«Чернетка»** для підготовки або **«Опубліковано»** для появи на головній. Згодом можна натиснути **«Опублікувати» / «Зняти з публікації»** без видалення запису.
5. У полі **«Виділяти на головній»** можна позначити важливі кадри: вони сортуються першими.

Публічна сторінка відображає **лише записи зі статусом «Погоджено»**; сервер повертає мінімальні дані, не передаючи службові поля `records.extra`. Користувачі можуть перемикати категорії й відкривати прямі фотографії у великому переглядачі. Учасники без `content:manage` не можуть редагувати або публікувати фотографії.

## Новини публічного сайту

Розділ **«Новини сайту»** доступний лідеру та ролям із дозволом `content:manage`. Це **окремий** тип записів `public_news`: старі внутрішні повідомлення з розділу **«Оголошення»** ніколи не переносяться на публічну сторінку автоматично.

1. У панелі виберіть **«Новини сайту» → «Нова публікація»**.
2. Заповніть **заголовок**, **текст**, оберіть категорію: Новина / Подія / Набір / Досягнення. Позначте важливі новини за потреби.
3. Спочатку збережіть **чернетку**, перевірте текст. Лише після вибору **«Опубліковано»** новина відобразиться на головній `https://grizzly-family.online/?view=public#news`.
4. Кнопка **«Приховати»** забирає публікацію з відкритої сторінки, не видаляючи запис із D1.

Новини віддаються через `GET /api/public` лише зі статусом `Погоджено`. Публічний API передає тільки заголовок, текст, дату, категорію та позначку важливості — без службових даних чи особових справ. **Нових таблиць D1 і міграцій не потрібно**.

## Керівництво на головній GRIZZLY

Публічна сторінка має секцію **«Керівництво»** за адресою **https://grizzly-family.online/?view=public#team**. Картки керівників створюються окремо від облікових записів та особових справ у D1.

1. Відкрийте в адмінпанелі **«Керівництво сайту»** → **«Додати керівника»**.
2. Заповніть **ігровий нікнейм**, **посаду** (наприклад, Лідер сім’ї, Заступник, Керівник CAPT), **короткий опис** та **порядок 1–99**. Чим менше число, тим раніше відображається картка.
3. За бажанням додайте **прямий HTTPS-URL персонажа з ImgBB** (вигляд `https://i.ibb.co/.../photo.webp`). Без фото відображається фірмове оформлення з першою літерою імені.
4. Виберіть **Чернетка** і збережіть або **Опубліковано**, щоб картка з’явилася на головній. Пізніше профіль можна приховати, оновити або видалити.
5. Оновіть публічну сторінку й перевірте картки.

**Безпека:** лише лідер і власники дозволу `content:manage` можуть керувати цими профілями. Через `GET /api/public` повертаються лише схвалені ігрові профілі з публічними полями: нікнейм, посада, опис, фото та порядок. Реальні особові справи, ігрові ID, Discord-акаунти, дозволи, паролі й інші дані користувачів не передаються. **Міграція D1 не потрібна**, використовується вже наявна таблиця `records` з типом `public_team`.

## Досягнення GRIZZLY

Для публічних перемог, нагород і визначних подій є окремий розділ **«Досягнення сайту»**. Публічний перегляд: **https://grizzly-family.online/?view=public#achievements**.

1. У панелі відкрийте **«Досягнення сайту» → «Додати досягнення»**.
2. Вкажіть назву, опис, **дату** та одну з категорій: **CAPT**, **Віхи**, **Події**, **Нагороди**.
3. Необов’язково додайте **прямий URL ImgBB** для обкладинки, наприклад `https://i.ibb.co/.../win.webp`; без зображення відображається тематична емблема.
4. Для перевірки збережіть **чернетку**. Після підтвердження відомостей використайте **«Опублікувати»** або виберіть «Опубліковано» у формі.
5. Керівник може **редагувати**, **приховати** або **видалити** досягнення. На публічній сторінці працюють категорійні фільтри та лічильники **лише опублікованих** записів.

**Принцип безпеки:** з CAPT не експортуються дані боїв, учасників, фінансів або внутрішні звіти. Досягнення додаються й підтверджуються керівництвом **вручну**, в окремому типі записів `public_achievements`. Публічний API повертає тільки затверджені назву, опис, категорію, дату, обкладинку та ознаку важливості. Для редагування необхідний дозвіл `content:manage`.

**Нових таблиць D1 та міграцій не потрібно** — використовується існуюча таблиця `records`.

## Нова структура публічного сайту

Замість однієї довгої сторінки сайт тепер має **компактну головну** та окремі публічні сторінки з навігацією через hash-маршрути.

| Розділ | Посилання | Що відображається |
|---|---|---|
| Головна | `#home` | Банер, короткий опис сім’ї, три переваги, три останні новини, заклик до вступу |
| Про сім’ю | `#about` | Історія, керівництво, напрямки та правила |
| Новини | `#news` | Усі опубліковані повідомлення, категорії та повний текст |
| Досягнення | `#achievements` | Підтверджені перемоги, нагороди, фільтри та підсумкові лічильники |
| Галерея | `#gallery` | Усі опубліковані фото, категорії, перегляд у великому форматі |
| Календар заходів | `#calendar` | Окремий публічний місячний розклад без зайвих блоків на головній |
| Вступити | `#join` | Анкета вступу, яка надсилається на чинний `POST /api/apply` |

Повне посилання для гостей, наприклад: `https://grizzly-family.online/#gallery`. Для перегляду з авторизованої панелі **без виходу з акаунта**: `https://grizzly-family.online/?view=public#gallery`. Старі посилання `#team`, `#directions`, `#rules` ведуть на сторінку **«Про сім’ю»** і прокручують до відповідного блоку.

Дані продовжують завантажуватися з чинного `GET /api/public`; публікація в адмінпанелі й права доступу не змінювались. Нові таблиці та міграції D1 не потрібні. Публічні сторінки — маршрути всередині тієї самої SPA, а не окремі HTML-файли.

## Публічний календар заходів

Публічна сторінка: **https://grizzly-family.online/#calendar**. Для перегляду без виходу з внутрішньої панелі: **https://grizzly-family.online/?view=public#calendar**. Календар має помісячну сітку, фільтри **Збори / CAPT / Тренування / Івенти** та розклад вибраного місяця. **На компактну головну додатковий блок не додається**.

### Як додати захід

1. Авторизуйтесь як лідер або користувач із дозволом `content:manage`.
2. Виберіть **«Календар сайту» → «Додати захід»**.
3. Заповніть **назву, опис, тип заходу, місце, дату й час початку** та необов’язковий час завершення.
4. **Усі введені дати й час трактуються як час Києва (Europe/Kyiv)** — без перерахунку часового поясу. Узгоджуйте цей час із командою.
5. Збережіть як чернетку для перевірки або опублікуйте. Після публікації захід з’явиться у публічному календарі.
6. Надалі можна **приховати, відредагувати або видалити** захід.

**Конфіденційність:** внутрішні `events` і CAPT-записи не копіюються до публічного календаря. Публічні записи зберігаються окремо в `records` з типом `public_calendar`, їх можна опублікувати тільки вручну. Відкритий `GET /api/public` повертає тільки статус `Погоджено` та мінімальний набір даних: назва, опис, категорія, час, місце. Не передаються власник, учасники, внутрішні поля чи службові примітки. **Міграції D1 не потрібні**.

## Фінальне оформлення публічного сайту

**Головний банер:** якщо у публічній галереї є хоча б одне опубліковане зображення з прямим HTTPS-посиланням ImgBB, банер підставить справжній ігровий скриншот як затемнене тло емблеми GRIZZLY. Перевагу має фото з позначкою **«Виділяти на головній»**. Якщо реальних фото поки немає, банер показує стилізовану емблему — нічого вигаданого не публікується.

**Як додати кадри:** у панелі **Галерея → Додати фото** вставте пряме посилання з `https://i.ibb.co/` на JPG/PNG/WEBP, вкажіть категорію та підтвердьте публікацію. Для головного фото увімкніть «Виділяти на головній». Зміни не потребують нової таблиці D1.

**Мобільна навігація:** під ширину 530 px кнопка «Особистий кабінет» переноситься всередину розкривного меню, щоб на вузькому екрані не конфліктувати з логотипом. Меню прокручується на невисоких телефонах, всі пункти доступні з клавіатури. Під час переходу між публічними сторінками змінюється заголовок вкладки, а фокус переводиться на основний вміст для користувачів клавіатури/екранних читачів.

**Публікація:** головна, новини, команда, нагороди та календар зберігають поточний публічний API й модерацію. УДО, внутрішні дані сім’ї та правила доступу не змінюються. Перевіряйте збереження і реальні зображення після розгортання Cloudflare.

## Discord-сповіщення керівництва

GRIZZLY надсилає в **приватний Discord-канал керівництва** повідомлення про нові заявки, рішення рекрутерів і публікацію заходів у календарі.

### Підключення webhook

1. Створіть приватний канал Discord (наприклад, #grizzly-kerivnytstvo). Доступ повинен бути тільки в керівництва.
2. Відкрийте **Налаштування сервера Discord → Інтеграції → Webhooks → Новий webhook**; виберіть цей канал і скопіюйте URL.
3. Відкрийте **Cloudflare → Workers & Pages → famaly → Settings → Variables and Secrets → Add**. Виберіть тип **Secret**, ім’я **DISCORD_WEBHOOK_URL**, значення — webhook URL. Збережіть та застосуйте нову конфігурацію.
4. Альтернатива через термінал у корені репозиторію: `npx wrangler secret put DISCORD_WEBHOOK_URL`.
5. Зайдіть як лідер у GRIZZLY → **Налаштування → Discord-сповіщення**. Натисніть **Надіслати тестове повідомлення** та перевірте приватний канал.

**Не вставляйте вебхук у код, GitHub, D1, публічні поля налаштувань чи чат.** Webhook — секрет із токеном.

### Які сповіщення надсилаються

- **Нова заявка:** ігровий нік та ID. Мотиваційний текст, контакт Discord і досвід не передаються.
- **Рішення рекрутера:** нік та новий статус, тільки якщо статус справді змінився. Коментар не передається.
- **Важливі події:** назва, час за Києвом та місце **лише після публікації** в «Календар сайту». Приватні заходи та CAPT-звіти не передаються.

Всі три типи активні за замовчуванням, якщо вебхук підключений. Щоб вимкнути окремий тип, додайте змінну середовища зі значенням `false`: `DISCORD_NOTIFY_APPLICATIONS`, `DISCORD_NOTIFY_DECISIONS` або `DISCORD_NOTIFY_EVENTS`.

**Захист:** Discord API отримує `allowed_mentions: {parse: []}`, тому не надсилаються згадки @everyone або ролей. Тільки лідер може дивитися статус і надсилати тест (до трьох разів за десять хвилин). URL не повертається API. Відправлення відбувається через Cloudflare Workers `ctx.waitUntil`, не затримує роботу сайту і не скасовує запис у D1 за помилки Discord. Доставка найкращими зусиллями, без постійної черги повторів.

## Керування Discord-сповіщеннями та журнал доставки

У панелі **лідер → Налаштування → Discord-сповіщення** з’явилися три окремі перемикачі: **Заявки**, **Рішення за заявками**, **Опубліковані події**. Вони зберігаються в D1; не потрібно змінювати webhook у Cloudflare, щоб увімкнути або вимкнути категорію.

**Потрібна нова міграція для робочої D1.** Спочатку оновіть код репозиторію, відкрийте термінал у корені `Famaly` та застосуйте лише нові міграції до правильної бази:

```bash
npm install
npm run migrate:remote
```

Це виконає нову міграцію `migrations/0003_discord_notifications.sql`: додасть три рядки до наявної таблиці `settings` та нову таблицю `discord_delivery_log`. Попередні заявки, рахунки, CAPT, учасники та webhook не змінюються. База УДО не використовується. **Перевірте, що `wrangler.toml` спрямований на `grizzly-db` та Worker `famaly`.**

Після успішної міграції розгорніть оновлений Worker через ваш Cloudflare GitHub deployment або командою:

```bash
npm run deploy
```

Перевірте **Налаштування → Discord-сповіщення**. Якщо бачите попередження про міграцію — вона ще не застосована до робочої D1. Якщо все готово, з’являться перемикачі, кнопка **Зберегти перемикачі** та журнал останніх 100 відправлень. Зміна одного прапорця не зупиняє інші типи. Оновлення захищені версіями D1: при одночасному редагуванні потрібно оновити сторінку.

**Журнал:** зберігає категорію (`applications`/`decisions`/`events`/`test`), час, `Надіслано` або `Помилка`, безпечний код проблеми та HTTP-статус за наявності. Токени, webhook URL, нікнейми заявників, мотивація, приватні коментарі та повний текст Discord-відповіді **не зберігаються**. Доступ до журналу — **лише лідеру**. Автоматично зберігаються не більше 300 останніх результатів; панель показує 100 найновіших. Попередні повідомлення не імпортуються.

**Наявні змінні Cloudflare:** якщо `DISCORD_NOTIFY_APPLICATIONS`, `DISCORD_NOTIFY_DECISIONS` або `DISCORD_NOTIFY_EVENTS` мають значення `false`, Cloudflare продовжує забороняти відповідну категорію, а перемикач у панелі буде недоступний, доки змінну не прибрано або не змінено. Керування не розкриває токен webhook.

**Доставка:** успішна відповідь Discord і запис у D1 журналу — незалежні операції. Якщо Discord тимчасово недоступний, основна заявка/рішення на сайті зберігаються, а журнал фіксує збій. Постійної черги для автоматичного повторного надсилання немає.

## Discord: CAPT-оголошення та новини сім’ї

До вже наявних типів Discord-сповіщень додано **CAPT-оголошення** та **Новини сім’ї**. Тепер у панелі лідера доступні **п’ять перемикачів**: Нові заявки, Рішення, Опубліковані події, CAPT-оголошення, Новини сім’ї.

### Як опублікувати CAPT-оголошення

1. Відкрийте **Новини сайту → Нова публікація**.
2. Вкажіть назву та опис. Оберіть категорію **CAPT-оголошення**.
3. Спершу можна зберегти **Чернетку**. Коли все узгоджено, натисніть **Опублікувати** або виберіть статус **Опубліковано**.
4. Discord відправить повідомлення типу **CAPT**, якщо перемикач CAPT увімкнений. Воно містить **лише заголовок**, а не внутрішні склади, бюджет, тактику, виплати чи приховані поля.

**Новини сім’ї:** аналогічно створіть матеріал у «Новини сайту», вибравши одну з інших категорій (Новина, Подія, Набір, Досягнення) та опублікуйте. У Discord піде окреме повідомлення типу **Новини**. Збереження чернетки або редагування вже опублікованого тексту не створює повторного повідомлення. Внутрішні CAPT-бої та звіти **не публікуються автоматично**.

### Міграція D1 — обов’язкова

Для нових перемикачів і журналу створено **`migrations/0004_discord_capt_news.sql`**. Вона додає налаштування `discord_notify_capt` та `discord_notify_news`, розширює типи журналу доставки й **переносить його наявні записи без втрати історії**.

У корені проєкту **Crowsk1ck/Famaly** виконайте:

```bash
npm install
npm run migrate:remote
npm run deploy
```

Wrangler застосує лише ще не виконані міграції (`0003` та/або `0004`). Перед застосуванням перевірте, що `wrangler.toml` вказує на Worker `famaly` і D1 `grizzly-db`, а не на УДО. Деплой коду без міграції призведе до попередження в інтерфейсі про незавершену міграцію; старі сповіщення за можливості продовжуватимуть відправлятися.

Додаткові вимикачі на рівні Cloudflare, якщо потрібні: `DISCORD_NOTIFY_CAPT=false` та `DISCORD_NOTIFY_NEWS=false`. За замовчуванням керування здійснюється з адмінпанелі лідера.

Webhook залишається тим самим Cloudflare Secret `DISCORD_WEBHOOK_URL`. **Не додавайте новий webhook і не публікуйте його токен.**

## 1. Створення окремого GitHub-репозиторію

1. Створіть у GitHub **новий приватний репозиторій** з назвою `Grizzly` (не `UDO`). Без README / `.gitignore` під час створення, бо ці файли вже є в архіві.
2. Розпакуйте `grizzly-site.zip` у власну папку (наприклад, `C:\Projects\Grizzly`).
3. У терміналі в папці виконайте:

```powershell
git init
git add .
git commit -m "Initial Grizzly family panel"
git branch -M main
git remote add origin https://github.com/Crowsk1ck/Grizzly.git
git push -u origin main
```

Якщо власник GitHub або назва інші — змініть лише адресу `origin`. **Не використовуйте** адресу репозиторію УДО. Репозиторій у вашому GitHub не створюється автоматично цим архівом.

## 2. Підготовка Cloudflare

Потрібні Node.js 20+ та Cloudflare-акаунт із доступом до Workers і D1.

```powershell
npm install
npx wrangler login
npx wrangler d1 create grizzly-db
```

Після `d1 create` Cloudflare покаже новий `database_id`. У `wrangler.toml` замініть:

```toml
database_id = "REPLACE_WITH_YOUR_OWN_D1_DATABASE_ID"
```

на ID **саме нової бази `grizzly-db`**. Не вказуйте D1 базу УДО.

Далі застосуйте схему й початкові редаговані налаштування:

```powershell
npm run migrate:remote
```

### Оновлення вже запущеного Grizzly — CAPT-календар і запис учасників

Після того як Cloudflare розгорне оновлення GitHub, потрібно **один раз застосувати** нову міграцію `migrations/0002_capt_signups.sql` до наявної бази `grizzly-db`. Це додає тільки таблицю записів CAPT і не видаляє учасників чи фінанси. Якщо міграції керуються Wrangler, виконайте у папці репозиторію:

```powershell
npx wrangler d1 migrations apply grizzly-db --remote
```

Якщо всі дії виконуєте через браузер, відкрийте GitHub → `migrations/0002_capt_signups.sql` → Raw → скопіюйте SQL, потім Cloudflare → D1 → `grizzly-db` → Console → Execute. Не запускайте повторно SQL `0001_init.sql` і не створюйте нову базу.

У панелі CAPT створіть бій і вкажіть **дату/час**, **кількість місць (1–50)**. Учасники відкривають бій у календарі й натискають «Записатися на бій». Перші N зареєстрованих потрапляють в **основний склад**, інші — в **резерв**; дублікати блокуються у D1. Для статистики позначайте завершений бій статусом **«Завершено»** та підсумком **«Перемога»**, **«Поразка»** або **«Нічия»**. Відсоток перемог враховує тільки завершені бої з явним результатом.

## 3. Перший лідер (одноразово)

Згенеруйте довгий випадковий токен у своєму терміналі:

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Запишіть цей токен **поза репозиторієм** і додайте його як Cloudflare Secret:

```powershell
npx wrangler secret put BOOTSTRAP_TOKEN
```

Wrangler попросить вставити токен. Після цього розгорніть Worker:

```powershell
npm run deploy
```

Він покаже URL на кшталт `https://grizzly-family.<your-subdomain>.workers.dev` (фактичний URL надає Cloudflare).

Для безпечного одноразового створення першого лідера у Windows PowerShell:

```powershell
$site = Read-Host 'Вставте URL нового Worker (https://...)'
$login = Read-Host 'Логін лідера (латиниця)'
$nickname = Read-Host 'Ігровий нік лідера'
$passwordSecure = Read-Host 'Пароль лідера (12+ символів)' -AsSecureString
$tokenSecure = Read-Host 'BOOTSTRAP_TOKEN із Cloudflare' -AsSecureString
$password = [System.Net.NetworkCredential]::new('', $passwordSecure).Password
$token = [System.Net.NetworkCredential]::new('', $tokenSecure).Password
$payload = @{ username=$login; nickname=$nickname; password=$password } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri "$site/api/setup/bootstrap" -ContentType 'application/json' -Headers @{ 'X-Grizzly-Client'='1'; 'X-Bootstrap-Token'=$token } -Body $payload
Remove-Variable password,token,payload
```

**Важливо:** створення першого лідера можливе лише коли база користувачів порожня. Після успішного запуску видаліть початковий секрет, якщо він більше не потрібен:

```powershell
npx wrangler secret delete BOOTSTRAP_TOKEN
```

Тепер відкрийте сайт, натисніть **«Особистий кабінет»** і увійдіть створеним логіном і паролем.

## 4. Локальний запуск

Для перевірки без публікації скопіюйте файл `.dev.vars.example` у `.dev.vars` (він ігнорується Git) і вставте власний токен мінімум 32 символи.

```powershell
Copy-Item .dev.vars.example .dev.vars
npm run migrate:local
npm run dev
```

Відкрийте `http://localhost:8787`. Якщо потрібен перший лідер у **локальній** D1, надішліть той самий POST-запит bootstrap, але з локальним URL та локальним токеном із `.dev.vars`. Локальна і віддалена бази — різні.

## 5. Щоденна робота

1. **Лідер:** «Склад сім’ї» → «Додати учасника». Заповніть нікнейм і натисніть **«Згенерувати логін»**, **«Згенерувати пароль»** (20 випадкових символів), виберіть роль і натисніть **«Створити акаунт»**. Відкриється **одноразове вікно** з готовими даними доступу, яке можна скопіювати й надіслати особисто. Після його закриття тимчасовий пароль не відновлюється з D1 — лише скидається. Генератор працює в браузері через Web Crypto, паролі надходять на сервер тільки для хешування, не зберігаються відкритим текстом. Роль у панелі не дорівнює ігровому рангу. У картці учасника можна обмежити права, заблокувати акаунт чи скинути пароль (при скиданні також показується одноразове вікно для копіювання).
2. **Учасник:** «Звіти та підвищення» → «Звіти» → «Додати запис», впишіть RP-дії й посилання ImgBB (кожне з нового рядка). Статус переходить на перевірку.
3. **Керівництво:** відкрити звіт → «Перевірити» → «Погоджено», «На доопрацювання» або «Відхилено». Рішення й коментар бачить автор у сповіщеннях.
4. **Контракти:** створити контракт, обрати учасників і суму → статус «Погоджено» → «Деталі» → перевірити попередній розрахунок → «Підтвердити нарахування». Система заборонить повторне проведення.
5. **CAPT:** відкрийте панель CAPT, де є зведені показники, найближчі бої та тренування, останні результати, відвідуваність і стан виплат. Створіть бій чи тренування, додайте відвідування, вкажіть `Бій` або `AFK`, погодьте запис → натисніть «Нарахувати CAPT». Після нарахування в деталях з'явиться позначка «CAPT-виплату проведено», повторної кнопки виплати не буде. Ставки беруться з «Налаштувань»; їх можуть бачити користувачі з правом керування фінансами. Для учасника показуються лише доступні CAPT-записи та власні виплати.
6. **Публічна сторінка:** лідер змінює Discord, правила, історію і ставки через «Налаштування». Фото додаються в «Галерею» за посиланням ImgBB; публічно відображаються лише записи зі статусом «Погоджено».
7. **Збереження:** всі зміни одразу записуються в D1; оновлення сторінки та робота з іншого пристрою не стирають дані. Якщо запис застарів, система попросить оновити його перед зміною.

## Обмеження

- Це підготовлений до Cloudflare Workers **повний код проєкту**, а не вже активний публічний вебсайт. Для онлайн-запуску потрібні ваш власний GitHub-репозиторій, база D1 та команда `wrangler deploy`.
- Браузерний інтерфейс і API протестовано локально; інтеграційні тести працюють на SQLite-адаптері, а не на живій Cloudflare D1. Після першого розгортання перевірте налаштування Cloudflare, ролі та доступ.
- Немає автоматичної публікації в Discord: шаблони копіюються вручну. Discord API/OAuth не потрібні.
- Внутрішня валюта — **ігрова**; це облік, а не платіжний шлюз.
