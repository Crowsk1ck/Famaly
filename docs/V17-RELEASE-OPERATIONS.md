## Як запустити перевірки локально

```bash
npm install
npm test
node scripts/check-performance-budget.mjs
bash scripts/check-backup-roundtrip.sh
npm install --no-save puppeteer-core
CHROME_PATH=/usr/bin/google-chrome node tests/panel-browser-acceptance.mjs
```

**Увага:** тест `panel-browser-acceptance.mjs` використовує **лише синтетичні облікові записи та локальну HTTP API-заглушку**, тому безпечно перевіряє інтерфейс на ПК і телефоні, але не підтверджує стан production-акаунтів. Справжні серверні правила перевіряє `npm test` в окремому інтеграційному середовищі SQLite.

## Захищений щотижневий backup D1

1. GitHub Actions `GRIZZLY private D1 backup` за розкладом або `workflow_dispatch` експортує **лише** `grizzly-db` після перевірки Worker/DB identity.
2. Експорт шифрується локально `AES-256-CBC` з `PBKDF2` (310000 ітерацій); passphrase — лише GitHub Secret.
3. Перш ніж відправити файл у **приватне backup-сховище R2**, workflow дешифрує його у тимчасовий файл, перевіряє точний збіг із початковим експортом і виконує локальне відновлення в одноразову SQLite-базу + `PRAGMA quick_check`.
4. Plaintext видаляється `trap` і перед завантаженням; журнал GitHub Actions не має містити SQL, паролі чи токени.

**Обмеження:** успіх синтетичного тесту в CI не означає, що реальний scheduled-backup вже запустився після змін. Перевірте зелений run `GRIZZLY private D1 backup` після оновлення v17.0 і наявність приватного об’єкта у сховищі. Ніколи не викладайте резервні файли у звичайні Actions artifacts або публічні посилання.

## Аварійне відновлення (тільки вручну)

1. Зафіксуйте інцидент і заблокуйте нові записуючі операції на час відновлення.
2. Оберіть останню **перевірену** резервну копію у приватному сховищі; завантажте її в захищене середовище. Не передавайте passphrase в чат.
3. Дешифруйте резервний файл локально з безпечним читанням secret з середовища.
4. Запустіть `python3 scripts/verify-d1-restore.py decrypted.sql` на локальній копії. Перевірте таблиці `users`, `records`, відновлюваність та дату копії.
5. Після перевірки визначте з керівником прийнятний ризик втрати новіших змін. **Жодний автоматичний імпорт у production D1 не виконується.** Відновлення в `grizzly-db` вимагає окремої явної згоди та резервної копії поточного стану.
6. Перевірте логін, ролі, особові справи, фінанси/контракти, Discord без тестових масових відправок.

## Розгортання і повернення до попередньої версії

- Злиття PR в `main` запускає `Verify Grizzly` та `GRIZZLY production deploy` (Worker `famaly`).
- Production workflow перевіряє Worker health, домен, зображення соцмереж та публічні переходи в Chrome з мобільною шириною.
- Відкат **коду** — через PR, що повертає перевірені зміни до останнього успішного коміту, та повторний CI + deploy. Ручне відновлення D1 не є автоматичним відкатом сайту.
- Якщо production deploy або браузерні перевірки неуспішні, реліз **не вважати завершеним**.

## Ручний приймальний чекліст після деплою

- Лідер: вхід, підрозділи, керівники, особові справи, дії з перевіркою версій.
- Заступник: редагування звичайного акаунта, заборона зміни акаунта лідера.
- Керівник: бачить свій підрозділ, не може змінювати чужі акаунти.
- Учасник: бачить склад сім'ї, може змінювати лише свій профіль.
- На телефоні: меню, модальні вікна, введення тексту, Esc/повернення фокусу за наявності клавіатури.
- Календар: час Києва, найближчі заходи, переходи; Discord: сповіщення без повторної доставки.
- D1: підтверджений запуск приватного backup з локальним restore-check.
